# Synthesized scenarios of blocks/ that fail on the interpreter of the same `ess`: the scenario
# is wrong, not the block. scripts/check-blocks-conform.sh reads this file, binds the list to
# the suite it runs (`ess-known-failures/1`) and passes it with `--known-failing`.
#
# A line `# root: <text>` opens a group and is the reason of every scenario id below it, up to
# the next such line. Every other line that starts with `#` is a comment. An id is written
# exactly; nothing is matched by prefix.
#
# The run fails when a scenario that is not listed fails, and it is refused (exit 2) when a
# listed scenario passes or is no longer in the suite: take the id off the list then. Each
# outcome a listed scenario was written for is reached by a hand-written scenario under
# blocks/scenarios/decision/, blocks/scenarios/policy/ or blocks/scenarios/work/.
#
# The three roots have one cause. A command that reads a related row through a stored field of
# the row it addresses (`when_related: {via: <stored field>}`) is synthesized by the strategy
# `arrange_related_row`. Synthesis refuses the outcome scenario of its accepting branch
# (ESS-SYNTH-008) and still writes the transition, state and invariant scenarios that run
# through that branch. In those it leaves an input that a `when_subject:` guard compares with a
# stored value at its default, and it points the act that created the addressed row at another
# related row without changing the inputs that act's own guards compare with it. The step is
# then answered by a refusal where the scenario expects the accepting branch (ESS-CF-OUTCOME).
